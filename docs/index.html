SQLHarness: Convert Business Instructions from Plain English to Executable SQL.

By Andrew Jorge

Overview

“Which region has the most customers?”
↓
SELECT r.name, COUNT(*) AS customer_count
FROM customers c
JOIN regions r ON c.region_id = r.id
GROUP BY r.name
ORDER BY customer_count DESC
LIMIT 1;

This project gives even the busiest professionals a simple way to extract any specific detail from their data—using only their own words. Ideally, decisions can be made instantly and with confidence, without needing to know anything about SQL.

SQLHarness approaches this in two parts: intent normalization and code generation. First the system translates the user's plain-English business request into a normalized semantic representation of the request calibrated around SQL primitives. This answers the question of “What's the universal way to describe this request without the specific business jargon?”. Afterwards, it translates the resulting normalized intent into real code through a governed boundary, minimizing the probabilistic effect of the model as much as possible.

The purpose of this brief is to demonstrate my research process of whether SQLHarness’ proposed architecture can improve the accuracy–cost frontier over direct LLM generation.

How the semantic model was developed

  • SQLHarness borrows a central idea from Abstract Meaning Representation (AMR): represent meaning as concepts connected by relationships.
    • I adapted that idea to database work, creating a smaller SQL-oriented graph that preserves what the user means in a form the rest of the system can inspect and act on.
  • GPT-6 Astra currently turns each request and its database context into that intent graph.
    • The study tests whether this intermediate representation is useful; replacing the frontier-model call with a dedicated smaller model remains future work.
  • The BIRD dataset provided the training data for the fragment ranker and the held-out data used to test whether each intent graph preserved enough meaning for SQL generation.
    • The training data connected each business question to its correct SQL. The held-out examples exposed gaps in the graph’s vocabulary, relationships, and grounding rules.

How the fragment ranker was developed

  • The ranker connects each concept in the intent graph to reusable SQL pieces that can express it.
    • This gives the assembler relevant building blocks instead of asking another model to generate the entire query from scratch.
  • The fragment ranker was trained on the BIRD dataset.
    • Each training example connected a business question to its correct SQL, showing the ranker which reusable SQL fragments matched each intent-graph concept and which plausible alternatives were incorrect.
  • The learned ranker was compared with a dense retriever, a simpler baseline that ranked fragments only by their embedding similarity to the intent concept.
    • Training improved the ranker’s first suggestion, but the dense retriever still returned the stronger candidate set overall. That result shifted the next priority toward expanding the fragment catalog and training evidence before adding more ranking complexity.

Making each query stage inspectable

A generated query can be valid SQL and still answer the wrong question. SQLHarness separates the request’s meaning, the SQL structures available for retrieval, and permission to execute. This makes a failure attributable to a stage instead of treating every wrong result as a prompt problem.

Following one request through the representation

The repository’s version 0.2 example represents “Which region has the most customers?” with a customer entity, a region attribute, a count operation grouped by region, and an argmax operation limited to one result. Directed edges connect the count to its customer target and region grouping; the output returns the region constrained by that maximum.

Retrieval uses the graph to select parameterized SQL building blocks; the assembler receives the graph, selected fragments, and database schema to propose SQL. The necessary operations here are joining customers to regions, grouping, counting, and selecting the largest group. One execution authority across interfaces

The Model Context Protocol (MCP) server and command-line evaluator call the same DatabaseAuthority. Every exposed execution tool uses these checks: database IDs resolve inside a configured root, SQL is parsed and checked against the schema and read-only policy, and allowed execution uses a read-only SQLite connection with a deadline and row cap.

MCP toolResponsibility
list_databasesList databases inside the configured authority root.
inspect_schemaReturn the selected database’s tables and columns.
validate_sqlCheck syntax, schema references, and policy without executing the proposal.
explain_sqlValidate the proposal before returning a bounded SQLite query plan.
execute_readonly_sqlValidate again, then execute under time and row limits.

Decisions include structured errors and deterministic receipt IDs for tracing. A receipt is an identifier for a decision, not a claim of immutable storage. Read-only enforcement limits database effects; it does not establish that an allowed query answers the business question correctly. Inspect the safety boundary and its limits.

What the failures changed

The five-query comparison exposed different ceilings: one parser timeout prevented assembly, and the 20-example fragment catalog contained only 58.82% of the exact SQL structures required by the held-out set. Ranking cannot recover a structure absent from the catalog. The learned ranker improved the first result but lost relevant structures farther down the list, without changing final correctness.

Those observations favor expanding the catalog and distilling the parser before further ranker tuning. Repeated teacher samples also had much less agreement on graph edges than nodes, so teacher graphs are treated as candidates to refine rather than unquestioned training labels. These are next research hypotheses, not measured improvements.
