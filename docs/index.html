Running a business is hard. In retail, you might find yourself with 2 hours to restock today's most popular item before customers find empty shelves. Your mind is already balancing tonight's staffing schedule and the recent arrival of that overseas delivery—and as soon as you switch focus, the house of cards will collapse, and you're spending extra time rebuilding the lost details.

Imagine if AI could help you mentally pick up right a task right where you left it. I built SQLHarness to help professionals automate the data retrieval part of that problem. If Claude Code can put together a working search bar for your website in less than 30 minutes, AI is clearly advanced enough to answer a simple question about your store data, right?

The purpose of this brief is to demonstrate the intuition behind SQLHarness’ proposed architecture: intent normalization and code generation. Every user input is broken into atomic semantic parts that make sense outside of the business context. Then it weaves those parts together into real SQL code, and runs it on your data to deliver a grounded answer to your original input task.

How the semantic model was developed

  • The graph structure was inspired by Abstract Meaning Representation (AMR). AMR looks past word order and keeps the underlying event: what happened, who or what caused it, and who or what it affected.
    • “A manager approved the budget” becomes three connected ideas: approve is the event, manager is the doer, and budget is the thing approved.
    • “The budget was approved by a manager” produces the same map because the meaning is the same.
  • SQLHarness applies the same idea to database questions. Its intent graph captures the data, calculation, rules, and requested answer in a shared graph format that can be checked against the database and translated into SQL.

How SQL fragments are selected

  • The intent graph becomes a parts list for the SQL query. Each labeled connection between two nodes describes one job, such as count customers, group them by region, or return a region name.
  • For each connection, SQLHarness searches a catalog of ready-made SQL pieces. It scores the candidates and keeps the piece that best fits both nodes, their relationship, and the database.
  • The selected pieces are joined into one query. If the catalog lacks a needed piece, the query cannot be completed—so the catalog must cover the SQL patterns the system may need.

Graph validation checks
  • There is exactly one output format node.
  • Every node has a name, an allowed type, and exact source words—or is marked as inferred.
  • Every connection joins real nodes with a supported relationship in an allowed direction.
  • There are no duplicate nodes or connections, self-links, cycles, or disconnected nodes.
  • Every database match names a real table or field in the database map.

How it works
Read the connection
count→ theme →customers

This says “count the customers.” The theme names what the operation acts on.

Find SQL templates for that job

The catalog pairs descriptions of jobs with reusable SQL. A count operation narrows the search to options such as:

COUNT({column_1})COUNT(*)

The braces mark a field to fill in during query assembly.

Rank the matching templates

The ranker scores matching words and applies fixed preferences. Here it slightly favors counting a named column, so COUNT({column_1}) comes first. COUNT(*) can count these customers too.

The graph’s database match supplies customers.id. During assembly, that field fills the selected template:

COUNT({column_1}) → COUNT(customers.id)

The other connections find what to return, how to group it, and how to order or limit the results.

What the study found

In the final five-query comparison, direct generation answered four correctly; both structured variants answered three.

The intermediate graph and fragments made failures easier to locate, but did not improve the accuracy–cost tradeoff in this small study. All variants used the same execution controls.
