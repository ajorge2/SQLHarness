SQLHarness: Talk to your business data.

By Andrew Jorge

Overview

User Input: “Which region has the most customers?”
↓
SELECT r.name, COUNT(*) AS customer_count
FROM customers c
JOIN regions r ON c.region_id = r.id
GROUP BY r.name
ORDER BY customer_count DESC
LIMIT 1;
↓
System Output:
Northeast (3 customers)
Example of English-to-SQL translation

This project gives even the busiest professionals a simple way to extract any specific detail from their data—using only their own words. Ideally, decisions can be made instantly and with confidence, without needing to know anything about SQL.

SQLHarness approaches this in two parts: intent normalization and code generation. First the system translates the user's plain-English business request into a normalized semantic representation of the request calibrated around SQL primitives. This answers the question of “What's the universal way to describe this request without the specific business jargon?”. Afterwards, it translates the resulting normalized intent into real code through a governed boundary, minimizing the probabilistic effect of the model as much as possible.

The purpose of this brief is to demonstrate the intuition behind SQLHarness’ proposed architecture.

How the semantic model was developed

  • SQLHarness begins with a simple idea borrowed from Abstract Meaning Representation (AMR): describe meaning as connected concepts instead of one block of text.
  • For a database request, those concepts answer four practical questions: What data is involved? What should happen to it? What rules apply? What should the answer look like?
  • The key design choice was to define this shared vocabulary—and the ways its parts may connect—before choosing the model that creates the graph.
  • A language model can draft the graph, while a separate validator rejects anything incomplete, disconnected, or tied to database fields that do not exist. That keeps the request's structure visible and checkable even if the model changes.

How SQL fragments are selected

  • Once the intent graph is ready, the system uses each concept to search a catalog of reusable SQL pieces.
  • A small ranking model then orders the matches from strongest to weakest. It considers their meaning, shared words, the kind of SQL operation, and the fragment type.
  • The catalog comes first: the ranker can choose among existing pieces, but it cannot recover a SQL pattern that is missing. Development therefore focuses on making the catalog broad and reliable before making the ranking model more complex.

What the study found

In the final five-query comparison, direct generation answered four correctly; both structured variants answered three.

The extra structure made failures easier to locate and execution easier to govern, but it did not improve the accuracy–cost tradeoff in this small study.
